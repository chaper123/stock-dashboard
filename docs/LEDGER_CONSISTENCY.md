# 記帳一致性方案（第 B 批：R02 後續＋R19）

> 狀態：**D1～D4 使用者 2026-11-07 說「全部照建議」，已在本機實作並驗證**（見第 5 節）；網站還沒部署，Apps Script 還沒更新（測試帳本驗證後才更新正式帳本）。使用說明與驗證步驟在 [LEDGER_WRITE.md](LEDGER_WRITE.md)。
> 依據：使用者轉貼的第 B 批要求與 6 個驗收案例、第三方報告 R02／R19、`apps_script/ledger_write.gs`（R02 版，已上線）、正式帳本的結構與公式（2026-11-07 唯讀讀取）。
> 原則：不換技術架構（仍是 Apps Script＋Google 試算表＋靜態網站），不改帳本既有的欄位與公式，不改晨報提示詞，只用測試帳本測。

## 一句話

**交易紀錄是唯一的事實來源。** 每次網站寫入，先在新的「寫入紀錄」分頁記下要做什麼（含持倉改前、改後），做完才標「完成」。中途壞掉，下一個拿到鎖的請求照紀錄補完；補不了就停下來，標「需要對帳」。錯帳不刪、不改原列的數字，加一列數字相反的「沖銷列」。

| 驗收案例 | 靠什麼做到 | 見 |
|---|---|---|
| 1 相同請求同時送兩次，只新增一筆 | 鎖內查「寫入紀錄」（持久，不再只靠 6 小時快取） | 2.2 |
| 2 已寫入但回應遺失，重開網頁仍查得回 | 新的「查詢」動作只讀寫入紀錄；重開記帳頁自動查 | 2.4、2.7 |
| 3 同一編號、內容不同，明確拒絕 | 寫入紀錄存內容雜湊，永久比對 | 2.2 |
| 4 交易列寫了、持倉更新途中故障 | 先記「處理中」與改前改後；恢復時看帳本實際狀態補完，不重複記帳 | 2.3 |
| 5 錯帳更正可追溯，同步股數、成本、資金 | 沖銷列＋原列標記；持倉照規則回推；可用資金由帳本公式自動跟著變 | 2.5 |
| 6 交易流水、持倉、資金按明確規則核對 | 7 條對帳規則，網站按一下就跑（唯讀） | 2.6 |

## 1. 現況（正式帳本，2026-11-07 唯讀讀取）

- **交易紀錄** A:P 共 16 欄。基準日（設定 B5）前的 9 列「計入資金池＝否」，而且大多沒有交割金額（個別手續費未提供）。
  → **持倉的總成本沒辦法從交易紀錄逐筆重建。** 持倉 E 欄是券商確認過的總成本，網站寫入是在它上面加減。
- **持倉**已經有股數核對：H 欄「交易紀錄股數」＝同代號買進股數減賣出股數（SUMPRODUCT），I 欄「股數差異」＝D－H。現在 4 檔都是 0。
- **可用資金**（設定 B15）＝基準日資金＋記帳前零頭＋累計入金－買入合計＋賣出回收。買入、賣出合計是 `SUMIFS(交易紀錄 K, L="是", D="買進"/"賣出")`。
  → **交易紀錄一變，可用資金就自動跟著變，不用另外寫資金。**
- **讀交易紀錄的地方**：
  - 網站 `data.js`（組合績效 `perf.js`、K 線成交標記、持倉頁交易表、本月紀律、記帳頁）。
  - 晨報 v4：讀 `'交易紀錄'!A1:N`，跑 `engine/discipline.py` 算本月買進合計。
  - 帳本自己的公式。
- 正式帳本目前**還沒有網站寫入的交易**：都是手動或「使用者回報」補記的，所以沒有舊資料要轉換。

## 2. 方案

### 2.1 帳本加兩樣東西（不動既有欄位）

1. **新分頁「寫入紀錄」**：每個網站寫入請求一列，不刪、不覆蓋。不發布成 CSV。

   | 欄 | 內容 |
   |---|---|
   | 請求編號 | 網站產生的隨機編號 |
   | 動作 | 新增交易／改定投／沖銷 |
   | 內容雜湊 | 請求內容的 SHA-256（R02 已在用的算法） |
   | 狀態 | 處理中／完成／需要對帳／已人工處理 |
   | 收到時間、完成時間 | 台北時間 |
   | 交易紀錄列 | 寫到第幾列（沒有就空白） |
   | 代號 | 只有新增交易、沖銷才有 |
   | 持倉改前、持倉改後 | 股數／總成本。新代號的改前是「沒有這列」 |
   | 請求內容、回應 | JSON。不含密鑰：密鑰不在 data 裡 |
   | 說明 | 恢復或需要對帳時寫原因 |

2. **交易紀錄最後加兩欄**：Q「請求編號」、R「更正」。
   - 網站寫的列填請求編號；手動記的列留空。
   - 「更正」欄寫「沖銷第 N 列」或「已被第 M 列沖銷」。
   - A:P 不動，所以持倉、設定的公式和晨報（只讀到 N 欄）都不受影響。

### 2.2 寫入流程（全部在鎖裡）

1. 拿鎖（照舊等 20 秒，拿不到就回「帳本正在寫入」，`retry: true`）。
2. **先把卡在「處理中」的舊請求恢復**（見 2.3）。整個寫入都在鎖裡，所以拿到鎖時還看到「處理中」，就代表那次執行已經中斷。
3. 用請求編號查寫入紀錄：
   - 雜湊不同 → 拒絕：「這個編號已經用在另一筆內容」（案例 3）。
   - 已完成 → 回傳當時的結果，標 `repeated`（案例 1、2）。
4. 驗證內容，算好持倉改前、改後，**先寫一列「處理中」**（含改前改後與請求內容），然後 flush。
5. 加交易列（Q 欄填請求編號），flush。
6. 更新持倉，flush。
   - 新代號的持倉列一次寫完，不再先複製上一列再改值，免得中途壞掉留下一列重複的舊代號。
7. 寫入紀錄改「完成」並存回應。快取照舊存一份，當作鎖外的快速路徑；真正的依據是寫入紀錄。

改定投（`setMonthly`）也照這個流程記一列，只是沒有持倉的部分。試算（`dryRun`）和測試連線不記。

### 2.3 中途壞掉怎麼恢復（案例 4）

恢復**看帳本實際狀態決定**，不看程式停在哪一行：

| 交易紀錄有這個請求編號的列？ | 持倉該代號現在是 | 處理 |
|---|---|---|
| 沒有 | （不用看） | 當作沒寫過：紀錄標「未寫入」。用同編號重送時照一般流程重新驗證、寫一次 |
| 有 | 改後 | 只差標完成 → 標「完成」 |
| 有 | 改前 | 持倉改成改後 → 標「完成」，說明寫「恢復：補更新持倉」 |
| 有 | 兩者都不是 | **不動持倉**，標「需要對帳」，說明寫現在的值。代表中間有人在網站外改過持倉，程式不猜 |

- 恢復在兩個時機發生：同編號重送或查詢時，以及**任何下一個寫入請求拿到鎖時**（2.2 第 2 步）。
  所以就算使用者再也沒回來確認那筆，帳本也不會長期失衡。
- 「需要對帳」的請求會出現在對帳結果裡（2.6）。使用者到試算表處理完，把狀態改成「已人工處理」。這一步交給教學 session 帶。
- **故障注入只放在本機假服務**：讓假的試算表在第 N 次寫入時丟錯誤。正式程式裡不加任何「故意失敗」的開關。

### 2.4 查詢寫入結果（案例 2）

新增動作「查詢」：帶請求編號和原本的內容，**只讀寫入紀錄、不寫交易**（但會順便恢復卡住的那筆，見 2.3）。

- 回「完成＋當時的結果」：結果裡有第幾列和持倉改前改後。
- 回「沒有收到這筆」：伺服器確定沒寫。
- 回「需要對帳」。
- 回「內容不符」：編號對、內容不同。

因為寫入紀錄是永久的，現在記帳頁「送出超過 5 小時就不能再重送」的限制可以拿掉。

### 2.5 錯帳更正：沖銷（案例 5）

新增動作「沖銷」：指定交易紀錄第幾列，同時帶上那列的請求編號或內容雜湊，防止列號錯位沖到別列。另外要寫原因。

**沖銷列怎麼寫**（建議做法，要你決定，見 D2）：

- 日期、市場、代號、買賣、成交價、幣別、計入資金池跟原列一樣。
- 股數、手續費、交割金額、台幣金額、交易稅都是**原列的負數**。
- Q 欄是這次的請求編號，R 欄寫「沖銷第 N 列」，備註寫原因與更正日。
- 原列只在 R 欄補「已被第 M 列沖銷」，**數字一個都不改**。

這樣帳本既有的公式全部自動正確：持倉的交易紀錄股數會少掉、設定的買入合計會少掉，所以可用資金加回來。晨報 v4 的本月買進合計也自動抵消（同月份同買賣）。日期用原交易日，所以「本月已投入」扣在正確的月份。

**持倉怎麼回推**：

- 沖銷買進：股數減原股數、總成本減原交割金額。
- 沖銷賣出：股數加回原股數、總成本加回當時減掉的成本（從寫入紀錄的改前改後取得）。
- 只要這列下面沒有同代號、還沒被沖銷的賣出，這樣算就是精確的。後面的買進只是加法，不影響結果。

**例子**：假設 11/05 那筆 009816 89 股記錯。

| | 改前 | 沖銷後 |
|---|---|---|
| 持倉股數 | 1,241 | 1,152 |
| 持倉總成本 | 17,196 | 15,887 |
| 可用資金 | — | 加回 1,309 |
| 交易紀錄 | — | 多一列 −89 股、−1,309，原列標「已被第 M 列沖銷」 |

**規則**：

- 只沖台股、計入資金池＝是、有交割金額的列。基準日前的列成本不明，不能從網站沖。
- 這列下面有同代號、還沒被沖銷的賣出，就拒絕，並說明要先從最後一筆賣出往回沖。賣出會把平均成本往下傳，順序亂了成本就不精確。
- 沖銷賣出需要當時減掉多少成本：網站寫的賣出可以從寫入紀錄取得；手動記的賣出沒有紀錄，請到試算表處理（教學 session 帶）。目前帳本沒有任何賣出。
- 沖銷後持倉不能變負。
- 一列只能被沖一次，沖銷列不能再沖：要改回來就重記一筆。
- 沖銷走同一套請求編號、寫入紀錄、恢復、查詢。
- **重記**：沖銷完成後，網站把原內容帶進記帳表單讓你改，再照一般新增送出（用另一個請求編號）。兩筆各自防重複。

### 2.6 對帳規則（案例 6）

記帳頁新增「對帳」按鈕，呼叫 Apps Script 的「對帳」動作。這個動作**只讀**，讀的是當下的帳本，不是延遲 5 分鐘的 CSV。每條規則回報 ✓ 或列出不符的列：

| # | 規則 | 範圍 |
|---|---|---|
| C1 | **股數**：每個代號的持倉「股數（券商確認）」＝交易紀錄買進股數－賣出股數（含沖銷列）。就是現有的 H、I 欄。交易紀錄有、持倉沒有的代號，或持倉重複的代號，也列出 | 台股＋美股 |
| C2 | **成本鏈**：每個代號，最後一筆完成的網站寫入的持倉改後＝現在的持倉。不同就列「上次網站寫入後持倉在試算表被改過」。這是提醒，不是錯誤，因為照券商確認改持倉本來就合理 | 網站寫過的代號 |
| C3 | **資金池欄位**：基準日之後的列要「計入資金池＝是」而且台幣金額有值；基準日之前的列要「否」 | 全部 |
| C4 | **台股交割金額**：買進＝價金＋手續費；賣出＝價金－手續費－交易稅；台幣金額＝交割金額。價金容許 ±1 元（零股價金的進位方式） | 台股、有交割金額的列 |
| C5 | **寫入紀錄對交易紀錄**：完成的紀錄都找得到同請求編號的列；有請求編號的列都有完成的紀錄；沒有「處理中」或「需要對帳」 | 網站寫入 |
| C6 | **沖銷配對**：每個沖銷列都指到存在的原列、數字剛好相反、原列有標記；一列沒有被沖兩次 | 沖銷列 |
| C7 | **資金重算**：用交易紀錄重算買入合計、賣出回收，和設定 B13、B14 一致（防止公式被改壞） | 全部 |

**美股**：網站暫時不做美股輸入。對帳頁的美股部分只做 C1、C3，並列出各檔的「確認日」。說明寫明：美股的配息、手續費、賣出、更正都在試算表維護，最近一次券商確認是哪天（R19）。美股配息再投入怎麼記，等第 C 批 R08 確認股利記法後再加進對帳規則。

### 2.7 網站（記帳頁與讀取端）

- **未確認的那筆**：重開記帳頁就自動「查詢」（不寫入）。
  - 查到完成：顯示結果並清掉。
  - 沒收到：給「送出」和「放棄」。
  - 需要對帳：說明怎麼處理。
  - 拿掉 5 小時限制。
- **寫入成功後**顯示「已寫入第 N 列，網站上的帳本數字約 5 分鐘後更新」，畫面先用伺服器回傳的改後數字。之後重開頁面時看發布的交易紀錄有沒有出現這個請求編號，出現了才拿掉提示。期間不會讓人以為沒記到又記一筆（R19）。
- **最近交易＋沖銷**：列出最近 10 筆台股交易，可沖銷的有「沖銷」按鈕。先預覽持倉股數、總成本、可用資金會怎麼變，寫原因，確認後送出。完成後給「重記正確的一筆」。
- **對帳卡**：見 2.6。
- **讀取端認得沖銷**：
  - `perf.js` 現在只收股數大於 0 的列，沖銷列會被丟掉、原列卻還在，所以要改成原列與沖銷列都不算。
  - K 線不畫被沖銷的那一對。
  - 持倉頁交易表標「沖銷」「已沖銷」。
  - 本月紀律的合計會自動抵消，不用改。
- **晨報**：合計自動正確，不改提示詞。`engine/discipline.py` 的「本月買進」清單會出現一筆負數，把它標成「沖銷」的顯示調整，跟晨報 v4.1 一起做（v4.1 本來就要走一次性測試＋你同意的流程）。
- **賣出提醒**（R19「不要讓勸說阻止如實記錄已成交的事」）：現在的 5 秒勸說是你 11/05 要的，要不要改見 D4。

### 2.8 測試（只用測試帳本）

**本機假服務（自動，`tests/apps_script/`）**：

- 6 個驗收案例全部跑。
- 案例 4 在每個步驟之間各故障一次：寫完處理中、寫完交易列、持倉寫到一半、寫完持倉。每種都恢復成一致，重送不多寫。
- 沖銷的買進、賣出、拒絕條件。
- 7 條對帳規則各做一個會失敗的帳本。
- 舊 R02 版留下的快取還能用。

**測試帳本實測**（你操作，教學 session 一步一步帶；正式帳本完全不送測試交易）：

1. **同時兩次**：本機測試頁一次發兩個相同請求 → 交易紀錄只多一列。
2. **回應遺失**：照現在的手動驗證第 3 步。再用「查詢」確認，查詢只讀寫入紀錄，證明不靠快取。
3. **同編號不同內容**：測試頁用同一個編號改股數再送 → 拒絕，帳本不變。
4. **中途故障**：正常記一筆，然後在測試帳本手動做出「交易列寫了、持倉沒更新」的狀態：把持倉改回改前，寫入紀錄狀態改回「處理中」。網站用原編號查詢 → 持倉補成改後、紀錄完成、交易紀錄沒多一列。再做一次把交易列也刪掉的版本 → 當作沒寫過，重送只寫一次。
5. **更正**：沖銷一筆 → 多一列沖銷列、原列有標記，持倉股數、總成本和設定的可用資金都回到記那筆之前。再重記一筆正確的。
6. **對帳**：全部 ✓。在測試帳本手動改一格持倉股數 → 對帳指出 C1 不符。

**正式帳本**：部署後只按「測試連線」和「對帳」（唯讀）。

### 2.9 你要做的事（Apps Script）

1. **測試帳本**：照 LEDGER_WRITE.md 建副本、換測試密鑰、貼新程式、部署，跑 2.8 的 6 項，然後收尾。
2. **正式帳本**：貼新程式，「管理部署作業 → 編輯 → 新版本」，網址不變。
   - 權限範圍不變：還是只用試算表、鎖、快取、指令碼屬性，不會要求重新授權。
   - 第一次寫入時，程式自動建「寫入紀錄」分頁和交易紀錄 Q、R 兩欄的表頭（D1）。
3. 確認發布的交易紀錄 CSV 有新的兩欄。「等發布同步」的提示靠請求編號欄判斷。

全程交給教學 session 帶，跟 R02 那次一樣。

### 2.10 不做的事與已知限制

- **不做**：
  - 不換架構，不做美股網站輸入。
  - 不從交易紀錄重建持倉成本：基準日前沒有逐筆成本。
  - 不自動改手動記的列，也不在不一致時自動改持倉：只回報。
  - 不做登入；R03 照原約定。
