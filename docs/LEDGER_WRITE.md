# 網站記帳：Apps Script 寫入服務

2026-11-05 使用者提出、同日核准設計（PROGRESS 第 11 項）。網站「記帳」頁（`site/js/pages/record.js`）把一筆台股成交寫進共用帳本，並更新「持倉」；也可以改每月定投金額（下個月生效）。

## 架構

- 寫入服務是綁在「投資共用帳本」試算表上的 Google Apps Script 網頁應用程式，程式在 `apps_script/ledger_write.gs`（repo 只放程式，不放網址與密鑰）。
- 網站用 `text/plain` 的 POST 送 JSON（簡單請求，不會有 CORS 預檢）；回應會轉址到 `script.googleusercontent.com`，瀏覽器自動跟過去。
- 寫入密鑰：Apps Script 的指令碼屬性 `WRITE_KEY`＋使用者瀏覽器的 localStorage（`ledger.writeKey`）。不放試算表（帳本是公開發布的）、不進 git、不放網址參數。網址也只存在 localStorage（`ledger.writeUrl`），網站只接受 `https://script.google.com/macros/s/…/exec`。
- 密鑰錯 10 次暫停 10 分鐘；寫入時用 LockService 排隊。每個寫入請求記在帳本的「寫入紀錄」分頁，同一個請求編號隔多久重送都回傳上次的結果，不會重複寫入（第 B 批，見下面「一致性」；R02 版只有 6 小時快取）。
- 先「檢查這筆」（`dryRun`，Apps Script 照帳本最新資料試算、不寫入），再「確認寫入」。
- 網站讀帳本用「發布到網路」的 CSV，寫入後約 5 分鐘才看得到。

## 重送與確認結果（2026-11-07，改進報告 R02 的最小修補；第 B 批之後的做法見下一節）

Apps Script（`doPost`）：
- 只有正式寫入（`addTrade`、`setMonthly`，不是 `dryRun`、不是 `ping`）才查重。快取 `req:<編號>` 存 `{ v: 2, hash, out }`：`hash` 是這筆請求內容（action＋data，鍵排序後序列化，不含 `dryRun`）的 SHA-256。
- 鎖外先查一次快取（快速路徑），**取得鎖之後再查一次**：兩個相同請求同時到、都在鎖外查不到時，先拿到鎖的寫入，後拿到的在鎖內查到結果，不會再寫。
- 同一個編號、內容相同：回傳原結果並標 `repeated: true`。內容不同（或換了動作）：回 `{ ok: false, conflict: true, error: "這個請求編號 6 小時內已經寫入另一筆內容不同的資料，這次沒有寫入。…" }`，不寫入。
- 這次沒處理到這筆的錯誤（密鑰錯、密鑰錯太多次暫停中、還沒設 `WRITE_KEY`、帳本正在寫入別的資料）標 `retry: true`，表示修好後可以用同一個編號再送；內容檢查失敗不標，也不進快取。
- 更新部署前存的舊格式快取（沒有 `hash`）照舊回傳 `repeated`，最多 6 小時後就不會再出現。

網站（`site/js/ledger_write.js`、`site/js/pages/record.js`）：
- 按「確認寫入帳本」時，**送出前**先把 `{ id, data, at, url }`（請求編號、成交內容、送出時間、目標 Apps Script 網址）存進這台裝置的 localStorage `ledger.pendingTrade`。**不存寫入密鑰。**
- 結果分三種：成功 → 清掉；Apps Script 明確拒絕（內容不對、同編號不同內容）→ 清掉並顯示原因；逾時、連線中斷、HTTP 錯誤、回應不是 JSON → 不知道有沒有寫入，保留。
- 有保留的那筆時（包括重開記帳頁），「記一筆成交」上方顯示「上次送出的這筆還沒確認結果」，有兩個按鈕：「用原編號確認寫入結果」（同一個編號、同一份內容再送一次：已經寫入就回傳原結果、不會重複寫；還沒寫入就這次寫入）和「放棄」（只刪掉這台裝置上的紀錄，帳本不動）。處理完之前「檢查這筆」不能按，避免重新填一筆變成兩筆。
- 確認時遇到 `retry` 類的錯誤（密鑰錯、帳本忙碌）或還是不知道結果：紀錄留著，可以再按。
- 送出超過 5 小時（Apps Script 的重複保護是 6 小時）就不再重送，請使用者先到帳本「交易紀錄」找這筆：有就「放棄」，沒有就「放棄」後重新填一筆。
- 紀錄的網址和目前的記帳連線不同（例如當時連的是測試帳本）時不能確認，只能改回原網址或放棄。
- 每月定投金額沒有保存未確認的請求：重送同一個金額會被「已經是這個金額」擋下，不會多一列。

## 一致性：寫入紀錄、中途恢復、沖銷、對帳（第 B 批，2026-11-07）

方案與規則在 [LEDGER_CONSISTENCY.md](LEDGER_CONSISTENCY.md)（使用者 2026-11-07 同意 D1～D4 照建議）。程式的做法：

- **寫入紀錄**：帳本新分頁「寫入紀錄」（第一次正式寫入時程式自動建，放在最後一個分頁），每個寫入請求一列：請求編號、動作、內容雜湊、狀態（處理中／完成／未寫入／需要對帳／已人工處理）、時間、交易紀錄列、代號、持倉改前／改後、請求內容、回應、說明。不含密鑰。
- **交易紀錄多兩欄**：Q「請求編號」（網站寫的列才有）、R「更正」（「沖銷第 N 列」「已被第 M 列沖銷」）。也是第一次正式寫入時自動加表頭；A:P 不動，帳本公式與晨報（讀 A:N）不受影響。
- **寫入順序**（全部在鎖裡）：先把卡在「處理中」的請求恢復 → 查寫入紀錄（雜湊不同拒絕；完成就回傳原結果）→ 記「處理中」→ 寫交易列（帶請求編號）→ 更新持倉（新代號整列一次寫完再補公式）→ 標「完成」。改定投也記一列，備註寫「網站輸入（請求編號 …）」。
- **中途恢復**：看帳本實際狀態決定。交易紀錄找不到這個編號＝沒寫過（標「未寫入」，重送照一般流程寫一次）；持倉是改後＝補標完成；持倉是改前＝補成改後；兩者都不是＝不動持倉、標「需要對帳」。同編號重送、查詢、或任何下一個寫入請求都會觸發。寫到一半出錯時回 `unknown: true`（網站當成「不確定有沒有寫入」）。
- **查詢**（`status`）：帶 `{ id, action, data }`，只讀寫入紀錄、不寫交易，回 `done`（附當時結果）／`none`（沒收到）／`check`、`manual`。編號放在 data 裡，所以 R02 版收到時只會回「不支援的動作」，不會被當成同編號的另一筆。
- **沖銷**（`reverse`）：指定交易紀錄第幾列，並帶那列的日期、代號、買賣、股數、交割金額核對。加一列沖銷列（股數、手續費、交割金額、台幣金額、交易稅取負，日期用原交易日），原列只在「更正」欄標記；持倉照規則回推（買進：減股數、減交割金額；賣出：加回股數與當時減掉的成本）。只沖台股、計入資金池＝是、有交割金額、下面沒有同代號未沖的賣出；手動記的賣出不能沖。
- **對帳**（`reconcile`）：只讀，7 條規則（股數、成本鏈、資金池欄位、台股交割金額、寫入紀錄對交易紀錄、沖銷成對、資金重算），另外列美股股數差異與確認日。
- **網站**：重開記帳頁有未確認的那筆時先自動查詢（不寫入）；寫入後記住「等發布」直到發布的 CSV 出現那一列；「記錯了？沖銷一筆」；對帳卡；`data.js` 的 `loadTrades` 拿掉沖銷的一對（績效、K 線、持倉頁、本月紀律都讀它），記帳頁用 `loadTradeRows` 看全部的列。
- `ping` 回報 `version: "2026-11-B"`。網站和 R02 版一起用時：查詢回「不支援的動作」就照舊用原編號重送（保留 5 小時限制），沖銷與對帳顯示「Apps Script 還是舊版」；測試連線會提醒更新。

新網站與舊 Apps Script、舊網站與新 Apps Script 都可以一起用，兩邊可以分開部署。

### 已知限制

- 未確認的那筆只記在送出的那台裝置與瀏覽器（例如手機送出、電腦看不到），一次只記一筆；換裝置請用對帳或直接看試算表。
- 「寫入紀錄」和帳本在同一份試算表，手動亂改還是會壞；對帳的 C5 會抓到。帳本如果是「整份文件」發布到網路，這個分頁也看得到（內容是編號、雜湊和交易資料，沒有密鑰）。
- 設定 B17「最近一次買入日」用 MAXIFS 找買進的最大日期：被沖銷的那筆如果正好是最近一次買進，仍會顯示它的日期。
- 「需要對帳」要人到試算表處理：照券商資料改好持倉，把寫入紀錄那列的狀態改成「已人工處理」。
- 記帳頁的「等發布」與沖銷清單讀的是正式帳本的發布 CSV；連到測試帳本時，清單只看得到正式帳本已有的列加上這台裝置剛寫入的列。

- `ledger_write_test.html`：自動測試，頁面標題會顯示 `PASS n/n`（第 B 批後 43 項）。第 B 批的 6 個驗收案例：同時送兩次、快取不見只剩寫入紀錄也只寫一筆、回應遺失後查詢、同編號不同內容、中途故障（交易列前、交易列後持倉前、持倉後標完成前、新代號補公式前、改定投；中斷後下一筆別的寫入先補完；持倉被手動改過標需要對帳）、沖銷（買進、手動記的買進、先沖賣出再沖買進、各種拒絕、中斷後補標記）、對帳（7 條規則各做一個會失敗的帳本）；讀取端拿掉沖銷的一對；網站和 R02 版相容。原本 R02 的項目：同編號連送兩次只寫一筆、兩個請求都在鎖外查不到後依序取得鎖只寫一筆、同編號不同內容（含換動作、鎖內才發現）被拒絕、`dryRun` 不查重不寫快取、`setMonthly` 重送、舊快取格式、鎖被占用回 `retry`、密鑰錯與內容錯、`ping`；網站部分測 localStorage 只存編號／內容／時間／網址（沒有密鑰）、壞掉的紀錄、回應遺失後用原編號重送只寫一筆、錯誤分類。網址加 `?src=/tmp/ledger_write.old.gs` 可以拿舊版對照（先 `git show <舊版>:apps_script/ledger_write.gs > tmp/ledger_write.old.gs`；`tmp/` 不進 git）：2026-11-07 修補前的版本在競態與同編號不同內容幾項會失敗。

## 用測試帳本驗證（使用者做，正式部署前）

本機測試用的是假服務。上正式帳本前，先用帳本的副本實際跑一次。

### 建立測試帳本

1. 開「投資共用帳本」→「檔案」→「建立副本」→ 名稱改成「投資共用帳本（測試）」→ **不要**勾「與相同使用者共用」→「建立副本」。綁在帳本上的 Apps Script 專案會一起複製；**部署作業不會複製**，所以副本一開始沒有網址，不會動到正式帳本。
2. 在副本開「擴充功能」→「Apps Script」，把左邊 `程式碼.gs` 全選刪掉，貼上 main 的 `apps_script/ledger_write.gs`（GitHub 上開檔案按「Raw」或複製鈕；還沒 push 時用本機 repo 的檔案）→ 儲存。
3. 換一組測試用的密鑰（不要和正式的一樣，免得網址貼錯也能寫進去）：本機預覽的記帳頁 →「⚙ 記帳連線」→「產生密鑰」複製；副本的 Apps Script →「專案設定」→「指令碼屬性」→「新增指令碼屬性」`WRITE_KEY`＝這組 → 儲存。
   - 2026-11-08 實際建副本時，指令碼屬性**沒有**跟著複製，副本裡沒有 `WRITE_KEY`，要新增。萬一看到已經有 `WRITE_KEY`，那是正式密鑰，一定要改掉，不能沿用。
   - 按「產生密鑰」後，密鑰只放在輸入欄裡，要到第 5 步按「儲存並測試」才會存起來；中間重新整理或關掉分頁就會不見。這個分頁先別關；不見了就到副本的指令碼屬性把 `WRITE_KEY` 複製回來。
4. 副本的 Apps Script →「部署」→「新增部署作業」→ 網頁應用程式、執行身分「我」、誰可以存取「所有人」→「部署」→ 授權（同第一次設定的第 6 步）→ 複製網頁應用程式網址。
5. 本機預覽網站（`.claude/launch.json` 的 `site`，或 `py -3.14 -m http.server 8765 --directory site`）→ 開 `http://localhost:8765/#/record`（以前開過的話先按 Ctrl＋Shift＋R，免得 service worker 給舊版畫面）→「⚙ 記帳連線」貼上測試網址與測試密鑰 →「儲存並測試」，**一定要看到「✓ 連線成功：『投資共用帳本（測試）』」**，名稱不是測試帳本就停下來。localhost 的記帳連線和正式網站（GitHub Pages）是分開儲存的，不會影響手機或正式網站的設定。

注意：本機記帳頁上方的「本月已買」等數字讀的仍是正式帳本的發布 CSV（只讀）；「檢查這筆」的試算與寫入都在測試帳本。

### 手動驗證步驟（第 B 批，都在測試帳本）

照上面建立測試帳本（第 2 步貼的是第 B 批的版本）。網站記帳頁按「測試連線」，**不能出現「這個 Apps Script 是舊版」的提醒**。

A. 網站記帳頁（`http://localhost:8765/#/record`，連到測試帳本）：

1. **試算不寫入**：填一筆買進 →「檢查這筆」→ 測試帳本「交易紀錄」列數不變，也還沒有「寫入紀錄」分頁。
2. **正常寫入**：「確認寫入帳本」→「✓ 已寫入交易紀錄第 N 列」。測試帳本：多一列、Q 欄是請求編號；最後多了「寫入紀錄」分頁，那一列狀態「完成」；交易紀錄 Q、R 兩欄表頭是「請求編號」「更正」；「持倉」股數與總成本更新、公式欄還在。
3. **回應遺失後查詢**：再填一筆 →「檢查這筆」→ 按「確認寫入帳本」後馬上關掉分頁 → 重開記帳頁 → 自動「用原編號查詢結果中…（不會寫入）」→ 顯示「這筆之前已經寫入過（交易紀錄第 N 列）」，**測試帳本只多一列**。關太慢的話重開後不會出現；再做一次，按完馬上關。
4. **沒送到**：填一筆 →「檢查這筆」→ 開發者工具（F12）→「Network」改成「Offline」→ 按「確認寫入帳本」→ 改回「No throttling」→ 重新整理記帳頁 → 自動查詢後顯示「Apps Script 確定沒有收到這筆」→ 按「用原編號送出」→ 這次才寫入，只多一列。
5. **放棄**：照第 4 步用 Offline 送出，重開後按「放棄」→ 帳本沒變。不要用第 3 步的「送出後關分頁」來測：那時請求可能已經寫進帳本，看不出「放棄」有沒有作用。
6. **每月定投金額**：先「測試連線」確認是「投資共用帳本（測試）」（正式帳本的定投金額會影響新聞晨報）→ 改一個金額 →「確定」→ 測試帳本「定投金額」多一列（下個月生效），備註是「網站輸入（請求編號 …）」，E、F 欄有公式；測完在副本刪掉這一列。記帳頁「每月定投金額」卡片讀的是正式帳本的發布 CSV，跟測試帳本對不上是正常的。

B. 實測頁 `http://localhost:8771/tests/apps_script/live_check.html`（`.claude/launch.json` 的 `tests`）：貼上測試帳本的網址與測試密鑰（只放在輸入欄，不會存），照順序按，每一步是「✓ 通過」才往下：

0. **測試連線**：帳本名稱要有「測試」、版本 `2026-11-B`，否則後面的按鈕不會開。
1. **同一筆同時送兩次**：只寫一列。
2. **同編號不同內容**：被拒絕。

## 網站的警告視窗（2026-11-05 使用者要求）

- 賣出（第 B 批 D4 起）：先問「這筆賣出已經在券商成交了嗎？」。「已經成交，照實記下」直接進預覽，提醒縮成預覽裡的一行；「還沒，只是想賣」才顯示原本的勸說：第一次買進台股到今天幾天、台股累計買進、配置紀律連續投入幾個月，預設按鈕是「我再想想，不賣了」，「我確定要賣出」要等 5 秒才能按。記帳是記已經發生的成交，勸說不擋如實記錄（改進報告 R19）。

## 動作

| 動作 | 內容 |
|---|---|
| `ping` | 測試連線，回傳帳本名稱、本月與下個月的定投金額、程式版本（第 B 批起 `2026-11-B`），不寫入 |
| `addTrade` | 「交易紀錄」加一列（日期、市場＝台股、代號（文字，保留前導 0）、買賣、股數、成交價、TWD、手續費、交割金額、台幣金額＝交割金額、計入資金池＝是、台幣金額來源＝網站輸入、備註、成交時間、交易稅、請求編號），再更新「持倉」：買進加股數與成本；賣出照平均成本扣，股數不夠就拒絕；沒有的代號整列一次寫完，再從上一列補公式。確認日只往後更新，來源欄尾端記「網站輸入：日期 買賣 股數」 |
| `setMonthly` | 「定投金額」分頁：下個月的列已存在就改那一列，沒有就新增一列（只寫四格，公式從上一列補）。備註「網站輸入（請求編號 …）」。分頁裡已經有更晚月份的列時拒絕，請到試算表手動調整 |
| `reverse` | 沖銷一列台股成交（規則見上面「一致性」與 LEDGER_CONSISTENCY.md）；`dryRun` 回傳持倉改前改後與可用資金的變化 |
| `status` | 用請求編號查寫入結果，不寫交易（會順便恢復中斷的請求） |
| `reconcile` | 對帳 7 條規則與美股股數差異，只讀 |

檢查規則：日期不能是未來；代號 4～6 碼數字可帶一個英文字母；股數正整數；成交價金是整數，和股數 × 成交價差不超過 1 元或 0.1%；手續費必填（可以是 0）；交易稅選填（預設 0）。交割金額：買進＝價金＋手續費＋交易稅，賣出＝價金−手續費−交易稅。

## 定投金額與新聞晨報（2026-11-07 依 v4 實際做法更正）

舊說法「新聞晨報的本月紀律固定用 3,000，改金額後要另外更新排程」已經不成立。實際做法：

- 網站改金額 → `setMonthly` 在「定投金額」分頁寫一列，生效月份＝下個月；這個月不變。
- 網站（總覽的本月紀律、記帳頁、行事曆、資金頁）讀帳本發布的 CSV，約 5 分鐘後更新。
- 新聞晨報 v4（2026-11-06 上線；平日 08:40 晨間、11:30 午間）每次執行都直接讀帳本「定投金額」分頁（`'定投金額'!A1:F`），交給 `engine/discipline.py --dca`。**改金額不用改排程、提示詞或程式。**
- `discipline.py`：某個月的金額＝生效月份不晚於這個月的最後一列（比第一列早用第一列）。輸出 `should_invest`（本月應投入）、`next_month_dca`（下個月）與 `dca_source`：帳本「定投金額」／CONFIG（沒有給 --dca）／CONFIG（帳本「定投金額」讀不到有效的列）。
- **從哪個月生效**：生效月份的第一個平日晨報起用新金額。例如 11 月改成 5,000，11 月的晨報仍是 3,000，12 月第一個平日（週末不跑）的午間晨報「本月應投入」就是 5,000。
- **晨報怎麼顯示**：紀律列只寫金額——午間每天一列，寫本月應投入多少、已投入多少；晨間只在入金日寫本月計畫的定投金額——正常情況不另外寫來源。只有「定投金額」分頁讀不到時，晨報不給 `--dca`、改用預設 3,000，並在摘要列註明「定投金額未取得」。
- **已確認與還沒遇過的**：2026-11-06 的 v4 一次性測試 run，午間的 `dca_source` 是帳本「定投金額」（PROGRESS 第 16 項）。目前分頁只有 2026-11 起 3,000 一列，「換月後改用新金額」還沒實際發生過；第一次改金額後，生效月份請看一下午間晨報的「本月應投入」。
- **定投設成 0（暫停）還沒定義**：網站與 Apps Script 允許 0。`discipline.py` 會把那個月當成已投入（門檻 0），也算進連續投入月數；如果「定投金額」分頁所有列都是 0，連續月數的計算會一路往回數到出錯（2026-11-07 本機確認），晨報紀律會變成「未計算」。要支援暫停定投，需要改 `discipline.py`（新 commit、新的釘選雜湊、一次性測試 run，並取得使用者同意）。
