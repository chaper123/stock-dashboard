## 3. engine 版本固定

排程用 raw 網址下載：`https://raw.githubusercontent.com/chaper123/stock-dashboard/<ref>/engine/<檔名>`。

| 方式 | 優點 | 缺點 |
|---|---|---|
| `main` | 不用維護 | 任何 push 都會立刻改變正式排程的行為，**不採用** |
| release 分支（例如 `engine-stable`） | 網址固定 | 分支會移動，事後難確認某天跑的是哪一版 |
| commit SHA | 完全不可變 | 網址難讀，更新時容易貼錯 |
| **tag（建議）** | 網址可讀、一版一個名字，報告與存檔可記版本 | 要記得打 tag；tag 理論上可移動（約定不移動） |

建議：tag `engine-v1.0`（monitor 規則 v1＋`run.py` schema 1），**另外在提示詞寫死三個檔案的 SHA-256**，下載後 `sha256sum -c`。tag 被誤移或 raw 快取出錯時，SHA-256 會擋下來。

- 下載失敗或 SHA-256 不符：不改用其他版本、不重打程式；報告置頂「⚠ 引擎無法取得，今日不計算訊號」，其他段落照常。engine 與行情來自同一個網域，兩者通常同時可用或同時失敗。
- 更新流程：使用者同意改規則 → 改 `engine/`、更新黃金檔並說明差異 → CI 綠燈 → 新 tag（`engine-v1.1`）→ 提示詞改 ref 與 SHA-256（屬於改排程，要先同意）→ 一次性測試 → 切換。
- `norm.py` 只在 v1 的鉅亨網備援用到，v2 不下載（保留在 `engine/` 供比對）。
- 版本與 tag 要等使用者同意 v2 方向後才打（這次沒有打 tag）。

## 6. 「儀表板資料」試算表（新，與帳本分開）

- 一份新的 Google Sheet，兩個分頁；排程只在最後面新增列，不改舊列。帳本照舊：美股只寫「估值快取」，台股不寫。
- 欄位由 `engine/run.py` 決定（`ARCHIVE_HEADER`、`PLAN_HEADER`，建立試算表前還能調整）：

| 分頁 | 一次寫入 | 欄位 |
|---|---|---|
| 報告存檔 | 每次執行 1 列 | 產生時間、市場、資料日、schema、engine（tag@SHA 前 12 碼）、可用資金、本次上限、規則參考合計、精簡 JSON、報告全文 |
| 配置計畫 | 每檔 1 列（美股 10、台股 3） | 產生時間、市場、資料日、代號、角色、狀態、等級、規則參考金額、約當美元、判定價、價格日、距第一買區上緣%、起始倉區、第一～深度買區、估值或溢價、原因 |

- 寫入步驟：報告寫好後 → `append_values` 報告存檔（最後一格填報告全文）→ `append_values` 配置計畫 → 再送出報告（資料備註寫入結果）。寫入失敗只重試一次，不影響送報告。
- 同一天重跑會多一組列；網站與配置器取同一個「市場＋資料日」裡產生時間最新的那組。
- 大小：精簡 JSON 美股約 4.5 千字、報告約 6～9 千字，都在單一儲存格 5 萬字的限制內；一年約 500 列存檔、3,300 列計畫。
- Phase 4 網站要讀這份時，需要使用者把它「發布到網路」。報告全文含新聞摘要與帳本數字（帳本數字已決定可公開），要不要一起公開請使用者決定。
- 測試期間寫到另外兩個分頁「測試_報告存檔」「測試_配置計畫」，正式切換後不再使用。

## 8. 測試與切換流程

每一步都要使用者同意，順序：

1. **同意 v2 方向與第 9 節的決定**（包含打 tag `engine-v1.0`）。
2. **建立「儀表板資料」試算表**（四個分頁：報告存檔、配置計畫、測試_報告存檔、測試_配置計畫），把 ID 填進 v2 草稿。
3. **一次性測試執行**：用 v2 草稿另建測試排程（RemoteTrigger create 後 run，不動正式排程），在 v1 正式執行的同一天、v1 跑完之後馬上跑（美股約 09:40、台股約 10:30），讓兩者讀到同一份 repo 資料。測試版和正式 v2 只差：
   - 報告標題加「【v2 測試】」
   - 不寫「估值快取」，儀表板資料寫到「測試_」分頁
   - 順便確認：pandas 版本、`append_values` 能不能用、WebFetch 能不能讀 MoneyDJ 美股 JSON 與櫃買中心（各試一次，不採用結果）
4. **比對**（用兩次執行的 run log）：
   - 引擎一致：拿 v1 的 config 在本機用 engine 跑同一份 market-data，輸出要與 v1 當天的程式輸出相同；v2 的 config 也一樣要與 v2 的 `monitor_out.json` 相同（這是 10/16 回放測試的做法）。
   - 輸入差異：逐欄比對 v1 與 v2 的 config（可用資金、持倉、匯率檔與數字、估值、event、溢價、盤中價）。每個差異都要對應到第 2 節列出的改動（例如估值改成每天、盤中價抓取時間不同），否則不通過。
   - 輸出：輸入相同的標的，狀態、等級、金額必須相同；不同的要能由輸入差異解釋。
   - 報告：各節齊全、數字有日期、資料備註有 engine 版本與 SHA-256 核對結果。
   - 執行：WebFetch／WebSearch 次數、耗時、錯誤、權限拒絕；試算表列數正確；沒有寫到不該寫的分頁。
   - 通過條件：引擎一致完全相同，其他差異都有解釋。不通過就修草稿再測一次。
5. **切換**：使用者同意後才用 RemoteTrigger update 改正式排程的提示詞（排程時間不變），v1 備份保留在 `private/routines/`。
6. **切換後**：第一週每天把正式執行的 config 在本機回放一次，確認與排程輸出一致；有問題就把提示詞改回 v1（一樣先問）。
7. 測試排程與「測試_」分頁在切換後由使用者決定是否刪除。

建議先切美股（改動多、收益大：程式碼 1.1 萬字、估值與匯率的 WebFetch），台股晚一到兩個交易日。

## 10. 已知限制與風險

- 排程環境的 pandas、numpy 版本未知；黃金測試固定在 pandas 3.0.6、numpy 2.5.4。版本不同時，完整輸出的小數尾數可能不同，但買區上下緣（四捨五入到 0.01）與金額（整數）不受影響的機率高；測試執行會印出版本，必要時在 CI 加測該版本。
- `valuation/us.json`、`chips/`、`holdings/` 只在完整抓取時更新；GitHub 排程整天沒跑時會是前一天的檔案，v2 的新鮮度檢查會改走備援或標「未取得」。
- 估值改成每天後，美股估值分級可能比 v1 早幾天改變（例如 VOO 本益比 10/12 快取 27.05 → 10/15 repo 24.58，分級都是「偏貴」）。
- 台股既有規則的行為照舊（未修改）：已持有的標的從第一買區因溢價降一級、或從等待因 boost 升一級，會落在「趨勢起始倉」等級拿 15%（10/16 的 00981A 就是這樣）。若使用者認為不合理，要另外同意改規則。
